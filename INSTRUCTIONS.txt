RULES FOR ALL RUNS
============================================================
- Professional, plain advisory tone. No overclaims. Every figure is
  current and sourced; anything unverifiable goes in the review note,
  not the content.
- No client names or data traceable to a client.
- Tribal-specific content only when the Topic says so.
- Research. Use only trusted, highly reputable sources, as broadly as
  the topic needs. Government primary sources are required for every
  rule, limit, deadline, and legal requirement; the other tiers add
  data, context, and practical guidance.
  Tier 1, primary (required for rules and figures): IRS, Treasury,
  DOL/EBSA, HHS, CMS, CDC, NIH, FDA, USDA (MyPlate, FoodData Central),
  OSHA, EEOC, SSA, OPM, IHS, CISA, NIST, eCFR, Federal Register,
  Congress.gov, GAO, CBO, healthcare.gov; state agencies (California:
  DMHC, CDI, FTB, EDD, CDPH, Covered California; Minnesota and
  Wisconsin insurance and revenue departments when relevant).
  Tier 2, research and nonpartisan data: KFF, EBRI, Commonwealth Fund,
  RAND, Peterson-KFF Health System Tracker, NAIC, Bureau of Labor
  Statistics, Census, peer-reviewed journals (JAMA, NEJM, Health
  Affairs, The Lancet), Mayo Clinic, Cleveland Clinic, American Heart
  Association, American Cancer Society, Academy of Nutrition and
  Dietetics.
  Tier 3, recognized industry and legal analysis: Mercer, Milliman,
  Segal, WTW, Aon, Business Group on Health, IFEBP, SHRM, PwC Health
  Research Institute, Insurance Information Institute, NCCI, AM Best,
  Verisk/ISO, and benefits-law firm client alerts (for example Groom
  Law Group, Proskauer, Littler, Jackson Lewis); tribal: NIHB, NCAI,
  Tribal Self-Governance Advisory Committee.
  Never cite: blogs, vendor or carrier marketing, press-release
  aggregators, social media, forums, AI-generated content farms, or
  Wikipedia. A Tier 3 claim about a rule must be confirmed in Tier 1.
  Survey figures name the survey, publisher, and year.
  Find pages with WebSearch. Read each source with WebFetch; if
  WebFetch fails or is unavailable, use the kit's fetch helper from
  the repository root, which works on sites that refuse automated
  tools:
    python3 fetch.py "<url>"                 page or PDF as text
    python3 fetch.py ecfr 45 147.130         current regulation text
    python3 fetch.py fedreg "search words"   newest Federal Register items
  Cite the exact URL you read. If a source still cannot be read after
  WebFetch and fetch.py, try a second primary source for the same
  fact; only then mark it UNVERIFIED in review.txt, quoting the exact
  FETCH FAILED message.
- Never send email, publish, or post anything. This task only drafts
  and saves files.

WORDPRESS FILES (Track A posts and every Track B post)

TRACK A - CLIENT NEWSLETTERS
============================================================
Audience: Atria's existing clients. These are NOT prospects.
- No marketing or prospecting language. Do not invite readers to
  "take a second look," "switch," "get a quote," or similar.
- Do not imply Atria has not already done work for the reader.
- Contact block: (507) 500-8377 | help@atriains.com | atriains.com
- Build every newsletter with the Atria build kit (see BUILD STEPS).
  The kit holds the approved layout, palette, fonts, logo, and contact
  block for each category; only the content changes.

Category rules:
- Benefits 101 and Well-Being: employee-facing, plain language.
- Well-Being: short article plus one very healthy recipe (low
  saturated fat, low sodium, low added sugar) from a public-domain
  source with a real photo. Put the photo link in the review note.
- Benefits Buzz and Compliance Corner: HR and CFO audience.
- Compliance Corner: no payroll items. State content defaults to
  California. Minnesota or Wisconsin items are allowed only if they
  meet the same relevance bar and state the specific requirement,
  who it applies to, the deadline, and a primary source. Be precise
  about applicability (example: the gag clause attestation is a
  self-funded plan obligation; carriers attest for fully insured).
- Prefer primary sources (IRS, DOL, CMS, HHS, USDA, state agencies).

Track A files (prefix every name with YYYY-MM-DD_[Category]_Issue[NN]_
using the send date). [Category] is hyphenated with no spaces:
Benefits-101, Well-Being, Compliance-Corner, Benefits-Buzz,
Risk-Report. Example: 2027-02-01_Benefits-101_Issue02_newsletter.pdf

3. wordpress.html  - Benefits 101, Benefits Buzz, Well-Being ONLY.

BUILD STEPS (Track A newsletters)
============================================================
The design lives in code in this repository (atriains/atria-newsletter-kit),
which is attached to the routine and cloned as the working repository.
Do not rebuild layouts by hand and do not edit atria-kit.js; only
write content. Never commit or push to the repository: keep issue.json
and all output in a separate folder outside it (~/out/[folder name]/).
1. Nothing to install: the kit's npm packages, icons, and fonts are
   inside the repository. Do not run npm install, apt, or any setup
   script. If atria-kit.js is not in the working directory, say
   "Build kit unavailable: repository not attached" in review.txt and
   the summary, upload the text files, and finish.
2. Read README.txt in the repository. Copy examples/[layout].json to
   issue.json and replace the content with this issue's content
   (layouts: benefits-101, well-being, compliance-corner,
   benefits-buzz, risk-report). Keep every key and every list length.
   The examples' facts are from Issue 01; never reuse them unverified.
3. Run ./build.sh issue.json [output folder]/[file prefix]. This makes
   newsletter.pptx, newsletter.pdf, and two QA page images.
4. Open both QA page images and check for overflow, overlap, or
   cut-off text. Fix by shortening copy in issue.json and rebuild.
   Never shrink fonts or edit the layout code.
5. Well-Being: never embed a photo. The PPTX keeps labeled photo
   frames; put the recipe photo URL in review.txt.
6. Risk Report uses a provisional layout: flag it in review.txt as a
   new template awaiting approval.
7. Write wordpress.html, email.txt, and review.txt from the final
   issue.json text so all versions match.

STEP 3 - SAVE AND DELIVER
============================================================
1. Folder name = the file prefix (YYYY-MM-DD_[Category]_Issue[NN] or
   YYYY-MM-DD_BlogPost_[short-slug], using the send/post date; TEST_ in
   front for test rows). Put every deliverable in ~/out/[folder name]/,
   and name each file with the full prefix, exactly:
     [folder name]_newsletter.pptx, [folder name]_wordpress.html,
     [folder name]_wordpress-post.txt (not for Compliance Corner),
     [folder name]_email.txt, [folder name]_review.txt (Track A; no PDF)
   or [folder name]_wordpress.html, [folder name]_wordpress-post.txt,
     [folder name]_linkedin.txt,
     [folder name]_review.txt
   (Track B). Not the kit's PDF, not issue.json, not QA images.
   Never create .md files. Track A review.txt starts with: "Review:
   edit the PPTX, then File > Export > PDF into this folder as
   [prefix]_newsletter.pdf before moving the folder to 2-Approved."
2. Upload them all to SharePoint in one command from the repository
   root:
     python3 upload.py "[folder name]" ~/out/[folder name]/*
   It never overwrites: if that folder already exists it uses
   [folder name]_v2 (then _v3, ...) and prints the folder it used on
   the FOLDER line; report that folder in the summary.
   It creates the folder and uploads each file through
   Microsoft Graph with the Atria uploader credentials in this
   environment, then prints OK or FAIL per file. Dustin set this up
   for this task; it writes only to 1-Review and never overwrites.
3. If any file prints FAIL (or the credentials are missing): upload
   the text files that failed with the Microsoft 365 connector
   (sharepoint_upload_file, content parameter) into the same folder,
   send the PPTX to the user with SendUserFile, and make the first
   line of review.txt: "Upload failed for: [files] ([error]). The
   PPTX is attached to the Claude run for [date]."
4. Update the history with the Microsoft 365 connector: read
   Atria-Content-Log.txt, add one line per piece drafted in this run
   (Draft date | Send date | Category | Issue | Topic | Angle | Example
   or persona | Headline), and save it back with sharepoint_update_file
   keeping every existing line. If you used an idea from
   Atria-Topic-Ideas.txt, add "USED [date]" to that line the same way.
   These two files are the only items outside 1-Review this task may
   change.
5. Never move, rename, or delete any existing SharePoint item. Never
   write to 2-Approved or 3-Published.
6. Send one push notification (PushNotification tool) before
   finishing: category, issue, topic, the 1-Review folder used, and
   any FAIL or UNVERIFIED item. Send it on success too, not only on
   problems.
7. Finish with a one-paragraph summary, the file list with OK/FAIL,
   and the link to the 1-Review folder.
